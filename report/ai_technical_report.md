# 속성 한방(Property Shot) — AI 활용 기술 문서

NAN 2026 Game × AI 해커톤 사전 과제

## 1. AI를 ‘작업자’가 아니라 ‘검증 가능한 제작 조직’으로 사용했다

속성 한방의 AI 활용 목표는 코드를 많이 생성하는 것이 아니었다. 사람의 게임 디렉팅을 중심에 두고, AI 에이전트를 기획 분석·구현·테스트·독립 감사 역할로 분리해 하나의 작은 제작 조직처럼 운영했다.

| 사람의 책임 | AI의 책임 |
|---|---|
| 재미의 정의, 난이도·기록 정책, 최종 선택 | 저장소 분석, 구현 후보, 반복 테스트, 문서화 |
| 어떤 실패를 허용하고 무엇을 보호할지 결정 | 물리·저장·접근성·화면 회귀의 위험 탐지 |
| 플레이 경험과 제출 메시지 승인 | 서로의 결과를 독립 감사하고 근거가 없으면 반려 |

공식 NAN 2026가 말하는 ‘AI의 다음 단계를 설계할 디렉터’라는 문제의식에 맞춰, 프롬프트는 단순 명령문이 아니라 역할·제약·증거·종료 조건을 가진 제작 계약으로 설계했다.

## 2. 프롬프트가 실제 작업으로 바뀌는 흐름

### 2.1 공통 제작 루프

1. **사용자 의도:** 불편, 재미 부족, 제출 요구를 자연어로 전달한다.
2. **계약화:** 루트 에이전트가 요구를 플레이어 가치, 보존 조건, 검증 기준으로 나눈다.
3. **전문 분석:** UI·레벨·물리·문서 등 담당 에이전트가 코드와 실제 화면을 조사한다.
4. **인간 결정:** 모호한 정책은 선택지를 비교하고 사람이 방향을 확정한다.
5. **구현:** 공유 파일 충돌을 피하도록 순서를 정해 기능과 테스트를 함께 수정한다.
6. **독립 감사:** 구현하지 않은 검사 에이전트가 P0/P1/P2로 문제를 분류한다.
7. **증거 루프:** 반려된 항목은 수정 후 같은 계약으로 재감사하고, 화면·영상·빌드까지 확인한다.

이 루프의 핵심은 ‘AI가 만들었다’가 아니라 ‘AI가 낸 결과를 다른 AI와 사람이 반증하려 했다’는 점이다.

### 2.2 실제 프롬프트를 작업 계약으로 바꾼 예

| 실제 프롬프트 발췌 | 계약으로 변환한 제약 | 수행·검증 결과 |
|---|---|---|
| “모바일에서는 손가락 때문에 게이지가 잘 안 보인다.” | 입력 임계값과 물리는 유지, 기물·SafeArea·저모션을 보호 | 부유 직선 게이지, 좌·우 선호, 접근성·Golden 검사 |
| “게임이 좀 어렵다. 튜토리얼을 조금만 더 쉽게.” | 캠페인 첫 학습만 완화, 오늘의 도전·리플레이·기록 공정성은 불변 | 기준 패턴 우선, 인과 힌트, 쉬움 예상 도착 표시 |
| “팁은 너무 추상적이면 안 된다.” | 정답 숫자 직행 금지, 패턴·버전·대상 기물에 결속 | 40패턴 L1/L2와 선택형 열쇠, 저장·복구 검증 |
| “모든 스테이지에서 기믹 활용이 매우 유리하도록 검증.” | 준비 전·후를 같은 입력 집합에서 비교, 실제 기믹 사건 필수 | 잘못된 1차 지표를 반려하고 레벨·검증 계약 재설계 |

프롬프트 전문과 결과 이력은 `harness_docs/prompts/prompt_history.md`에 요약되어 있으며, 원래 요구·역할별 지시·최종 변경 기록을 분리해 보존한다.

## 3. 주요 프롬프트 → 작업 → 결과

### 3.1 손가락에 가리는 파워 게이지

| 프롬프트 의도 | 수행한 작업 | 게임에 생긴 변화 |
|---|---|---|
| 모바일에서 공 주변 게이지가 손가락에 가린다 | 입력 상태기계는 유지하고 렌더 위치만 분리, 기물 겹침 회피와 좌·우 선호 설계 | 공 가까이에 보이되 홀·풍선·슬라이더·열쇠를 피하는 부유 직선 게이지 |
| 색 단계와 과충전 피드백을 유지한다 | 초록·노랑·빨강·경고·취소 상태, 저모션·점멸 설정, 접근성 문구 검사 | 색뿐 아니라 아이콘·라벨·눈금으로 상태 인식 |

![기믹을 피하며 경고 상태를 보여 주는 충전 게이지](../test/goldens/charge_gauge_stage4_warningRed_left_390x844.png)

독립 감사에서 퍼센트를 80ms마다 읽어 주는 접근성 과다 알림과, 실제 충전 전 50%가 보이는 불일치를 발견했다. live 상태와 non-live 퍼센트를 분리하고 450ms 실제 충전 시작 전에는 레일을 숨겨 해결했다.

### 3.2 게임이 어렵다는 피드백

| 프롬프트 의도 | 수행한 작업 | 게임에 생긴 변화 |
|---|---|---|
| 튜토리얼을 조금 쉽게 만든다 | 첫 1–4단계만 기준 패턴 우선, 물리·점수·셔플은 유지 | 첫 경험의 무작위 난이도 급등 제거 |
| 쉬움/보통을 나눈다 | 실제 판정기를 읽기 전용으로 재사용하고 기록 귀속을 분리 | 쉬움은 예상 첫 도착 표시, 보통 기록의 공정성 유지 |

![실제 판정 결과를 이용한 쉬움 모드 예상 위치](../test/goldens/difficulty_easy_first_arrival_390x844.png)

감사 과정에서 앱 재개 시 현재 설정이 완료 당시 난이도를 덮을 수 있음을 발견했다. 완료 건의 정체성에 난이도를 한 번만 귀속하고, 정상 완료·완료 복구·성공 직후 크래시 복구를 같은 규칙으로 검증했다.

### 3.3 추상적인 팁을 구체적인 플레이 도움으로

| 프롬프트 의도 | 수행한 작업 | 게임에 생긴 변화 |
|---|---|---|
| 어려운 스테이지에서 무엇을 해야 할지 모르겠다 | 40패턴별 L1/L2 HintCatalog, 대상 오브젝트와 행동 순서 검증 | L1은 기믹과 첫 행동, L2는 위치·세기·순서·예상 결과를 설명 |
| 팁을 선택적으로 얻고 싶다 | 다음 단계 팁 보상과 비물리 열쇠, 저장 성공 후 VFX | 필요한 플레이어만 도움을 선택하고 물리·점수는 그대로 유지 |

힌트는 `stageId + patternId + hintVersion`에 결속되어 잘못된 패턴의 답을 보여 주지 않는다. 열쇠 수집과 힌트 열람은 재시작·복구 뒤에도 유지된다.

### 3.4 기믹이 장식으로 끝나는 레벨

초기 프롬프트는 모든 단계에서 기믹 사용이 유리해야 한다는 것이었다. 첫 자동 검증은 서로 크기가 다른 입력 표본의 성공 개수를 비교하는 오류가 있었고, 독립 감사 에이전트가 이를 반려했다.

수정된 계약은 준비 전과 준비 후를 **같은 입력 격자**에서 비교하고, 같은 마지막 샷이 준비 전에는 실패하는지, 기믹을 실제로 사용했는지, 대표 해법 주변에도 성공 여유가 있는지를 함께 확인한다. 이 과정에서 단순히 테스트를 통과시키지 않고 문·스위치·슬라이더·점착 표면의 인과를 레벨 데이터와 물리에 다시 연결했다.

| 결과 | 의미 |
|---|---|
| 단발형 32패턴 각각 ≥1.40배 | 각 변형에서도 기믹 경로가 더 넓다 |
| 잔류 공 단계 합계 1.92배 | 첫 샷으로 준비한 상태가 다음 성공을 유의미하게 넓힌다 |
| 속성 통합 4패턴 모두 우위 | 스위치·문·점착·슬라이더의 준비가 핵심 해법이다 |

이 사례는 AI의 장점뿐 아니라, **AI가 만든 지표도 독립 검증 없이는 틀릴 수 있다**는 운영 원칙을 보여 준다.

### 3.5 시연 영상도 기능처럼 검증

영상이 반전되거나 쉬운 직선 클리어만 보여 주는 문제를 프롬프트로 전달했다. 이후 시연은 특정 탄성 패턴과 입력을 고정하고, 실제 브라우저 텔레메트리에서 열쇠·L1/L2·탄성 이전·다중 벽 반사·비직행 클리어를 확인해야만 합성할 수 있게 했다. 각 기능 장면은 2초씩, 전체 영상은 정확히 60초이며 방향 변환도 검사한다.

## 4. AI 협업 구조

| 역할 | 질문 | 산출물 |
|---|---|---|
| 통합 조정 에이전트 | 무엇을 어떤 순서로 합치고 충돌을 피할 것인가 | 계약, 우선순위, 통합 제안 |
| 기능 담당 | 이 요구를 현재 구조에서 어떻게 안전하게 구현할까 | 코드·단위 테스트·Golden |
| 레벨 담당 | 기믹이 실제 성공에 유리한가 | 동일-grid 지표, 대표 해법, 레벨 데이터 |
| 문서 담당 | 평가자가 5분 안에 가치를 이해할 수 있는가 | 게임·AI 보고서, 발표 자료 |
| 독립 검사 | 주장과 증거가 일치하며 회귀가 없는가 | P0/P1/P2 감사와 재검증 |

에이전트 수를 늘리는 것이 목표가 아니었다. 독립적으로 병렬화할 수 있을 때만 만들고, 공유 설정·저장·렌더 파일은 한 담당자가 통합했다. 작업이 끝난 에이전트는 중지해 토큰과 충돌을 줄였다.

### 4.1 사용한 AI 도구와 역할

| 도구 | 사용 방식 |
|---|---|
| Codex 코드 에이전트 | 저장소 탐색, Flutter/Dart 구현, 테스트·문서 파이프라인 실행 |
| gpt-5.6-terra 실행 에이전트 | 기능별 분석·구현과 표적 회귀 |
| gpt-5.6-sol 감사 에이전트 | 코드를 수정하지 않는 독립 P0/P1/P2 감사와 재검증 |
| 이미지 생성 도구 | 돌·젤리·상자 원본 생성; 투명화·권리대장·실제 번들 여부를 별도 관리 |

모델 이름보다 중요한 운영 원칙은 구현과 감사를 분리하고, 실행 증거가 없는 주장은 채택하지 않는 것이었다.

## 5. 게임과 AI 시스템 구조

| 계층 | 역할 |
|---|---|
| Stage data | 10단계·40패턴, 오브젝트·해법·힌트 메타데이터 |
| ShotResolver | 방향·힘·속성으로 결정론적 결과 계산 |
| RunState | 진행, 잔류 공, 보상, 힌트 권한, 열쇠 수집을 저장 |
| GameScreen / Flame | 입력·Canvas 렌더·접근성·피드백 |
| Validator / tests | 패턴 구조, 인과, 결정론, 화면, 복구, 기믹 우위 검증 |
| Report pipeline | PDF·A4 세로 PPT·영상의 재생성과 시각 검사 |

## 6. AI 활용의 구체적 성과

- 자연어 피드백을 40패턴 데이터와 실행 가능한 테스트 계약으로 전환했다.
- 물리·리플레이를 바꾸지 않고 쉬움 미리보기와 튜토리얼 완화를 추가했다.
- 접근성, 저장 복구, 기록 공정성처럼 화면만 봐서는 놓치기 쉬운 결함을 독립 감사로 발견했다.
- 잘못된 통계 검증을 스스로 반려하고 같은 표본공간의 지표로 다시 설계했다.
- 보고서·PPT·영상까지 코드와 같은 재생성·검증 파이프라인으로 관리했다.

## 8. 책임과 한계

- 최종 게임 규칙, 난이도 정책, 채택·반려 결정은 사람이 맡았다.
- 자동 테스트는 재미와 초보자의 감정을 대신하지 못하므로 외부 플레이테스트가 더 필요하다.
- 생성 이미지의 상업 사용 범위는 최종 법무 검토가 필요하다.
- iOS 실기기 장시간 성능과 App Store 제출은 이번 사전 과제 범위 밖이다.

## 9. 평가자가 확인할 수 있는 것

웹 플레이에서는 속성 이전과 장면 상태 변화가 실제 해법을 만드는지, 쉬움·게이지·힌트가 물리 규칙을 훼손하지 않고 도움을 주는지 확인할 수 있다. 이 문서와 60초 영상은 AI 활용이 단순 생성이 아니라 역할 분리·반증·재감사의 흐름이며, 그 결과가 실제 기믹 연쇄와 주요 기능으로 이어졌음을 보여 준다.
