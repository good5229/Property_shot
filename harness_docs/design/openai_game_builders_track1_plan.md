# OpenAI Game Builders Seoul Track 1 대응 계획

작성 기준: 2026-08-23 KST

## 목표

공식 심사축인 Playability, Originality, Codex Collaboration, Release Potential, Presentation에 맞춰 기존 수직 프로토타입을 브라우저에서 즉시 이해하고 플레이할 수 있는 공모전 빌드로 발전시킨다. 기존 프로젝트를 사용하는 만큼 챌린지 기간에 새로 개발한 기능은 별도 manifest로 구분한다.

공식 근거:

- [Track 1 진행·제출·심사 기준](https://openaigame2026.com/#apply:track-1)
- [OpenAI harness engineering](https://openai.com/index/harness-engineering/)
- [WCAG 2.2 드래그 대체 입력](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)
- [WCAG 2.2 색상 단독 의존 금지](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)
- [Hive SDK 공식 모듈](https://developers.withhive.com/HTML/v4_api_reference_en/Unity3D/modules.html)

## 구현 순서

1. 캠페인 저장과 분리된 60초 핵심 체험
2. 공이 얻은 속성과 원본이 잃은 속성의 동시 피드백
3. 첫 화면의 행동 수와 설명을 진행도에 따라 점진적으로 공개
4. 사람의 재미 목표 → Codex 후보 → Validator 반려/통과 → 사람 채택을 보여 주는 Puzzle Forge
5. 챌린지 기간 신규 개발 기능 manifest와 제출용 16:9 썸네일
6. 검증된 짧은 일일 변주와 향후 Hive 서비스 어댑터 경계
7. 핵심 제출 경로의 한국어·영어 UI와 PC·모바일 반응형 구성
8. 비정상 입력·저장 손상·다중 화면·브라우저 회귀

3분 영상은 사용자 요청에 따라 이 반복에서 제작하지 않는다.

## 60초 핵심 체험 계약

- 저장·로그인·메뉴 탐색 없이 홈 최상위 행동에서 시작한다.
- 실제 생산 패턴과 ShotResolver를 사용한다.
- `무거움 이전 → 비워진 원본 → 남은 공 재사용`의 세 장면을 고정 순서로 제공한다.
- 캠페인 진행, 보상, 발견, 리플레이 기록을 변경하지 않는다.
- 첫 입력 전 자동 클리어 상태가 없어야 한다.
- 각 장면에서 현재 순서, 단일 목표, 다음 행동을 짧게 표시한다.
- 320×568, 390×844, 768×1024, 1440×900 이상의 홈에서 핵심 진입을 가리지 않는다.

## 후속 품질 계약

- 속성 변화는 색뿐 아니라 형태·무늬·문구·Semantics로 구분한다.
- 드래그 조준에는 키보드와 버튼식 각도·힘 조절 대안을 유지한다.
- Web 심사 빌드는 로그인을 요구하지 않는다.
- Hive는 Flutter의 로컬 DB 패키지와 혼동하지 않도록 외부 게임 플랫폼 서비스 어댑터 뒤에 둔다.
- 실제 Flutter Web용 Hive SDK를 확인하기 전에는 연동 완료로 표현하지 않는다.
- 에이전트 대리 플레이는 비정상 입력과 발견 가능성 회귀에만 사용하고 실제 재미 검증을 대체하지 않는다.

## 제출 자료 계약

- 제출 필드는 팀명, 게임명, 200자 이하 게임 소개, 로그인 없는 HTTPS 플레이 링크를 한 문서에서 복사할 수 있게 유지한다.
- 기존 기능과 2026-08-04~2026-08-26 챌린지 기간 신규 개발 기능을 기계 판독 가능한 manifest에서 분리한다.
- 16:9 썸네일은 1920×1080 PNG와 10MB 미만을 자동 검사하고, 생성 프롬프트·입력 역할·해시를 함께 보존한다.
- Codex 협업 설명은 사람이 정한 재미 목표, Codex가 구현한 후보, Validator가 검증한 항목, 사람이 내린 최종 판단을 구분한다.
- 3분 이내 영상은 선택 항목이며 사용자 요청에 따라 이번 작업 범위에서 제작하지 않는다.
- Hive는 실제 연동이 확인되기 전에는 제출 문안에서 연동 완료로 표현하지 않는다.

## 양면 속성 변화 계약

- 속성을 옮긴 직후 원본의 `보유 → 비움`과 공의 `기본 → 획득`을 한 안내에서 동시에 보여 준다.
- 원본이 잃은 속성은 별도 상태로 보존해 팝업 설명, Semantics, 보드 표식이 같은 사실을 말하게 한다.
- 무거움·탄성·점착·뾰족함마다 원본의 물리 변화 결과를 구체적인 한 문장으로 알린다.
- 색에만 의존하지 않고 생성 이미지, 취소선 표식, 문구를 함께 사용한다.
- 안내는 보드를 가리지 않는 상단 흐름에 3초 동안만 나타나며 스크린 리더에는 하나의 live region으로 전달한다.
- 390×844와 768×1024 Golden 및 네 속성의 도메인·물리 회귀를 통과해야 한다.

## 홈 점진 공개 계약

- 초행 홈은 `60초 핵심 체험`, `첫 스테이지 시작`, `섬 지도 둘러보기`만 직접 행동으로 보여 준다.
- 첫 클리어 뒤 탐사와 스테이지 선택을 열되, 보상과 아직 잠긴 활동 설명은 접힌 `다른 활동` 안에 둔다.
- 세 스테이지를 익힌 뒤 같은 메뉴 안에서 리플레이와 오늘의 도전을 추가한다.
- 잠긴 활동은 사용할 수 있는 버튼처럼 보이지 않게 하고, 메뉴를 연 경우에만 정확한 해금 조건을 설명한다.
- 320×568부터 1920×1080까지 초행·중간·숙련 상태를 나눠 검증한다.

## Codex Puzzle Forge 계약

- `사람의 재미 목표 → Codex 후보 제작 → StagePatternValidator 반려·통과 → 사람의 최종 채택`을 앱 안의 순서도로 보여 준다.
- 사람 목표와 후보 의도는 `harness_docs/design/puzzle_forge_evidence.json`이 소유한다.
- 생성 도구가 실제 생산 카탈로그 40패턴의 정적·ShotResolver 실행 검증과 결함 변이를 수행한 뒤 제품용 JSON을 만든다.
- 제품 앱은 `tool/`이나 테스트 fixture를 가져오지 않고 생성된 `assets/forge/puzzle_forge_summary.json`만 읽는다.
- 시작 공–홀 겹침과 잘못된 문 연결 후보는 실제 안정 오류 코드가 검출될 때만 반려 사례로 표시한다.
- 기술 코드보다 플레이어가 겪을 결과를 먼저 설명하고, 검증 통과만으로 재미를 증명했다고 표현하지 않는다.
- 홈에서 진행 기록과 무관하게 접근할 수 있고 390×844·768×1024·1440×900 Golden을 통과해야 한다.
