# 10단계 확장 실행 계획

## 목표와 기준선

- 활성 목표: 4단계 데모를 데이터 기반 10단계 반복 플레이 제품 구조로 확장
- 기준 브랜치: `commercial/wall-physics-qa`
- 안정 단계 ID: `stage_heavy`, `stage_bouncy`, `stage_chain_gate`, `stage_balloon`
- 2026-08-06 기준선: `flutter analyze` 통과, 전체 테스트 252개 통과, Web Release 빌드 통과
- 현재 공백: 패턴 모델, seed·셔플 백, `RunState`, 패턴 검증기, 5~10단계, 신규 기물과 반복 플레이 시스템이 없음

## 공통 데이터 경계

구조화 포맷은 별도 의존성이 필요 없는 JSON을 사용한다. `StageDefinition`은 안정적인 단계 ID와 패턴 목록을 소유하고, `StagePattern`은 `patternId`, 가중치, 난이도, 논리 좌표 배치, 해법군, 선택 도전과 단계 메타데이터를 표현한다. 배치는 기존 `360×560` 논리 좌표를 사용하며 `LevelDefinition`으로 손실 없이 변환한다.

런마다 달라지는 `rootSeed`와 `patternSeed`는 정적 패턴 파일에서 생성하지 않는다. 이는 `PS-RUN-01`이 담당하고 `RunState`가 확정값을 저장한다. 패턴 파서는 구조와 enum 오류만 거부하며 배치·물리 유효성은 `StagePatternValidator`가 담당한다.

## 기존 문서 대체 관계

`harness_docs/readme.md`는 최초 수직 프로토타입의 원문이므로 삭제하거나 사후 수정하지 않는다. 다만 다음 표현은 활성 목표에서 역사적 기준으로 대체한다.

- `3개의 짧은 테스트 맵`과 `최소 3개`: 현재 목표는 10단계와 단계별 3~4개 패턴
- `장기 콘텐츠와 메타 시스템 제외`: 현재 목표는 런, 셔플 백, 보상, 오늘의 도전, 리플레이와 개인 기록 포함
- `상용 서비스 전체가 아닌 프로토타입`: 실제 스토어 제출은 범위 밖이지만 플레이·시각·저장·성능 품질은 상용화 수준을 목표로 함
- `iPhone 12`, `iPad Pro` 출품 완료 기준: 계속 중요한 화면·입력 참고 기기이나 현재 완료 판정은 실제 App Store 제출 여부와 분리
- 과거 테스트 수와 Web PID·번들 해시: 실행 당시의 역사적 증거이며 각 통합 시점의 최신 실행 결과로 다시 기록

새 목표가 기존 핵심 규칙을 폐기하지는 않는다. 속성 이전, 결정론적 판정, 한 손 조작, 계획과 실행 분리, 실패 공 누적, 복수 해법은 그대로 유지한다.

## 작업 의존관계

1. `PS-DATA-01`: 데이터 기반 단계·패턴 스키마. 모든 후속 작업의 선행 조건.
2. `PS-RUN-01`: 결정론적 seed와 단계별 셔플 백. `PS-DATA-01` 의존.
3. `PS-RUN-02`: 원자적 `RunState` 저장·복구·마이그레이션. `PS-RUN-01` 의존.
4. `PS-VALID-01/02`: 정적·대표 입력 검증과 invalid fixture·변이 메타 테스트. 데이터·런 구조 의존.
5. `PS-INPUT-01`, `PS-UX-01`: 프레임 독립 입력, 다단계 힘 게이지, 취소 상태.
6. `PS-OBJ-01/02`: 파워 슬라이더와 회전 반사판의 결정론적 이벤트·재생.
7. `PS-STAGE-01`: 기존 1~4단계를 각 3~4개 패턴으로 이전하고 레거시 경로를 회귀 고정.
8. `PS-STAGE-02~07`: 5~10단계 제작. 각 패턴은 배치 차이 기준과 복수 해법 검증을 통과해야 함.
9. `PS-SCORE-01`, `PS-REWARD-01`: 연쇄 점수·파밍 방지와 클리어 보상 3택1.
10. `PS-DAILY-01`, `PS-REPLAY-01`, `PS-UX-02`: 오늘의 도전, 공유 코드, 실패 인과 재생, 설정.
11. `PS-A11Y-01`, `PS-PERF-01`, `PS-QA-01`, `PS-DOC-01`: 접근성·감각 피드백, 성능, 전체 통합, 문서 동기화.

## 단계별 완료 게이트

- Luna가 구현 파일, 불변 조건, 테스트, 위험을 정해진 결과 형식으로 보고
- Sol이 diff에서 범위 이탈·결정론·레거시 호환·한글 UI를 직접 검토
- 집중 테스트와 관련 회귀 통과
- 통합 지점마다 `flutter analyze`, 전체 `flutter test`, `flutter build web --release` 통과
- 작업 결과와 원문 요구 대응을 `harness_docs`에 기록
- 한 작업 단위씩 commit 후 원격 브랜치에 push
- 서버 교체 시 기록된 PID가 실제 현재 프로세스인지 확인하고 기존 서버를 종료한 뒤 최신 Release만 실행

## 최종 완료 증거

10단계와 단계별 3~4개 패턴, 셔플 백·런 복구·재추첨 방지, validator와 실패 fixture, 신규 기물, 입력·점수·보상·일일 도전·리플레이·설정이 코드와 테스트로 확인되어야 한다. 각 단계의 복수 해법, 홀·벽·과거 공·연쇄 충돌 불변 조건, 저장 마이그레이션, Web Release와 최신 데모 HTTP 응답까지 확인한 뒤 Sol이 `GO`, `조건부 GO`, `NO-GO` 중 하나를 근거와 함께 판정한다.
